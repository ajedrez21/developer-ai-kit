Ejecución, validación y cierre de tareas

Criterio único para desarrollar, evidenciar y cerrar Work Items. Unifica revisiones, deja prueba de cada implementación y acorta el tiempo de validación.

1. Preparación del entorno 2. Procedimiento de ejecución 3. Evidencia obligatoria 3.1 Backend — Postman 3.2 Frontend — Jam 4. Carga de evidencia y cierre 5. Cambios posteriores

Para qué existe esta metodología

Cada desarrollo tiene que quedar implementado, probado, documentado y respaldado con evidencia, de modo que cualquier integrante del equipo pueda revisar lo hecho sin pedir una demo improvisada.

Regla corta Sin evidencia no se cierra la tarea. Backend: captura de Postman en el workspace compartido. Frontend: video corto de Jam con link. Los cambios de alcance van a una tarea nueva.

1. Preparación del entorno

Antes de tomar cualquier tarea hay que haber leído e instalado todo lo que indica la guía del kit. Esa configuración es obligatoria para trabajar con los lineamientos del equipo (Cursor, Node, PAT Azure como tl-control, OpenSpec, Postman y Jam).

Abrir “Cómo instalar y usar el kit”

No saltees este paso Si el kit, el PAT Azure o las herramientas de evidencia no están, el flujo de /work-item → /work-apply y el cierre con Postman/Jam no van a cerrar bien.

Con el entorno listo, mirá el video donde se explica el procedimiento que vamos a usar para ejecutar las tareas (contexto, plan, código, gates, commit).

Resumen del orden en el chat de Cursor, sobre el repo de la tarea:

  1. /work-item <id> — el CLI lee Azure con PAT (igual que tl-control), contexto y rama desde sandbox.
  2. /work-propose <id> — plan OpenSpec.
  3. /work-apply <id> — implementación. Correrlo es la aprobación para codear.
  4. /verify-change <id> y /security-review <id> --changes.
  5. /commit-change <id> y /pr-ready <id> — commit local; el PR se crea si lo pedís.
  6. Evidencia (Postman o Jam) y cierre de la tarea, según las secciones 3 y 4.

3. Evidencia obligatoria del desarrollo

A partir de ahora, todas las tareas tienen que tener evidencia de implementación y de que funciona, antes de cerrarse. El tipo de evidencia depende del rol.

Backend

Postman en el workspace compartido: endpoint actualizado, prueba con 200 OK cuando corresponda, y captura de esa ejecución.

Frontend

Jam: video corto de la funcionalidad, prueba rápida según lo pedido, y link para compartir.

3.1 Backend — validación con Postman

La colección vive en el workspace compartido del equipo. El alta al team está en la guía de instalación.

Unirme al team de Postman

  1. Obtener el token. Entrá a NWEB DEV, iniciá sesión y tomá el token de autenticación desde una consulta que ya lo mande (típico: header Authorization de una request autenticada, o el campo que indique el material de referencia). Pegalo en Postman como {{token}}. No lo commitees ni lo pegues en el chat del kit. La guía de instalación (sección 12) cubre el alta al team.
  2. Configurar Postman. Reemplazá la variable global {{token}} por ese valor. Quedate en el workspace del equipo, no en My Workspace.
  3. Registrar el endpoint. Si es una API nueva, agregala a la colección con un ejemplo de datos. Si es una API que ya existía, actualizá request, body y ejemplos.
  4. Validar. Ejecutá las pruebas que correspondan. En las operaciones exitosas que apliquen, la respuesta tiene que ser HTTP 200 OK.
  5. Evidencia. Captura de pantalla de esa ejecución: que se vean el endpoint, el código de respuesta y los datos devueltos.
  6. Guardar. La colección tiene que quedar actualizada en el workspace compartido para que cualquiera pueda repetir la prueba.
Resultado esperado Endpoint documentado y actualizado en Postman, con evidencia de que funciona.
Secretos El token es de tu sesión. No lo commitees, no lo pegues en el chat del kit ni en el Work Item. La captura no debería mostrar passwords; el token podés recortarlo si queda muy expuesto.

3.2 Frontend — validación con Jam

Usá Jam para dejar evidencia visual del cambio. La extensión se instala en Chrome; no corre dentro de Cursor.

Instalar Jam en Chrome

  1. Abrí la funcionalidad implementada o modificada (ambiente donde se pueda ver el cambio).
  2. Grabá un video corto con Jam que muestre qué cambió.
  3. Hacé una prueba rápida que permita comprobar que se comporta según lo pedido.
  4. Guardá el video y copiá el enlace para compartirlo. No subas el archivo al repo.
Resultado esperado Video breve con el que se vean los cambios y se pueda comprobar el funcionamiento.
Datos en pantalla No grabes passwords, tokens ni datos personales de producción. Si hace falta una cuenta de prueba, usá esa.

4. Carga de evidencia y cierre de la tarea

Cuando el desarrollo y las pruebas están listos:

  1. Adjuntá en la tarea la evidencia: captura de Postman (backend) o enlace de Jam (frontend).
  2. Verificá que la implementación cumpla con lo solicitado.
  3. Dejá registrados los cambios realizados (commit con referencia Azure, comentarios si hace falta).
  4. Cerrá la tarea.

Nueva modalidad de aprobación

No hace falta esperar una aprobación manual del Pull Request para cerrar la tarea, siempre que estén hechos: implementación, validación de funcionamiento y evidencia adjunta.

La evidencia demuestra que se desarrolló y se probó según lo definido. La aprobación técnica del código y los controles automáticos del repositorio (CI, políticas de rama) siguen valiendo cuando correspondan.

PR vs. cierre del Work Item El kit no pushea ni marca el ítem como Done. El cierre en Azure lo hace la persona, después de adjuntar la evidencia. El merge del PR sigue las políticas del repo.

5. Cambios o ajustes posteriores

Si en una revisión posterior Diego o José piden algo nuevo, un comportamiento distinto al definido originalmente, o un cambio de alcance, se abre una tarea nueva para esos ajustes.

Eso cubre cambios de alcance, definiciones nuevas y requerimientos extra. Si lo implementado no cumple los criterios originales o tiene un defecto, se corrige en la validación de esa misma tarea: no es alcance nuevo.

SituaciónQué hacer
No cumple lo pedido o hay un bug de lo implementado Corregir en la misma tarea, con evidencia nueva
Nueva definición, alcance extra, “mejor así” Tarea nueva; no reabrir el alcance de la anterior
