Cómo instalar y usar el kit en Backend y Frontend

Guía para unirse a los repos, instalar las herramientas externas, cargar el kit en cada proyecto y trabajar una tarea de Azure de punta a punta. Incluye el alta al team de Postman para backend.

1. Qué es este kit

El Developer AI Kit es un procedimiento común para Cursor y Claude Code. No cambia la arquitectura del producto: se instala encima de los repos de backend y frontend y deja skills, reglas y un CLI para trabajar cada Work Item de Azure de la misma forma.

El recorrido de una tarea es:

  1. /work-item — lee Azure, arma contexto y crea la rama desde sandbox.
  2. /work-propose — genera el plan OpenSpec.
  3. /work-apply — implementa ese plan. Correrlo es la aprobación para codear.
  4. /verify-change y /security-review — gates.
  5. /commit-change y /pr-ready — commit local y preparación del PR. No hay push automático.
Dos repos, dos instalaciones El kit se instala en cada repo de producto, no una sola vez en la máquina. Backend usa --role backend y frontend --role frontend.

3. PowerShell: usá npm.cmd y openspec.cmd

En Windows, si PowerShell tiene la política de ejecución restringida, npm y openspec fallan con “el archivo npm.ps1 no está firmado digitalmente”. No hace falta cambiar la política. Llamá al .cmd: 

npm.cmd -v
npm.cmd install -g @fission-ai/openspec
openspec.cmd --version

node y git no tienen ese problema. El resto de esta guía usa npm.cmd / openspec.cmd para que copie y pegue sin fricción.

4. Bajar los repositorios

Creá las carpetas si no existen y cloná. Las rutas de ejemplo coinciden con las del equipo; podés usar otras, pero entonces ajustá los --target del setup.

4.1 Kit (una vez por máquina)

mkdir "C:\Maxi\Repos Propios" -Force
cd "C:\Maxi\Repos Propios"
git clone https://github.com/ajedrez21/developer-ai-kit.git
cd developer-ai-kit
npm.cmd install
npm.cmd run build

npm run build deja el CLI en dist/cli.js. Sin ese build, el setup no corre. El kit no se “instala” como app: se usa desde esta carpeta para configurarlo en cada repo de producto.

4.2 Backend y frontend (repos de producto)

Hace falta acceso SSH a Azure DevOps. Si todavía no tenés clave cargada en el portal, Git va a pedir autenticación.

mkdir "C:\Maxi\Sistemas\Repos" -Force
cd "C:\Maxi\Sistemas\Repos"

git clone git@ssh.dev.azure.com:v3/DMEDLATSYS/NCSLite/NWebCore.Backend
git clone git@ssh.dev.azure.com:v3/DMEDLATSYS/NCSLite/NWeb.Frontend

En cada repo, trabajamos sobre sandbox (no sobre main):

cd C:\Maxi\Sistemas\Repos\NWebCore.Backend
git checkout sandbox
git pull

cd C:\Maxi\Sistemas\Repos\NWeb.Frontend
git checkout sandbox
git pull
Working tree limpio /work-item crea la rama de la tarea desde sandbox. Si hay cambios sin commitear, no cambia de rama. Antes de arrancar una tarea, commiteá o stashé lo ajeno.

5. Paquetes y herramientas externas

Esto se hace una vez por máquina, salvo OpenSpec init, que se corre en cada repo de producto.

5.1 OpenSpec (CLI global)

El kit no implementa el plan: llama a OpenSpec. Sin este CLI, Cursor no tiene /opsx-propose ni /opsx-apply.

npm.cmd install -g @fission-ai/openspec
openspec.cmd --version

Tiene que mostrar una versión (en el equipo se validó 1.14.1).

5.2 Azure CLI (login para el MCP de Azure DevOps)

El kit lee Work Items por el servidor MCP ado-developer, autenticado con Azure CLI. No se guardan PAT en el repo.

az --version
az login
az account show

Si az no existe, instalá Azure CLI y volvé a abrir la terminal. El login abre el navegador de la cuenta con la que accedés a DMEDLATSYS.

5.3 Skill de seguridad security-compliance

El kit no copia el auditor: lo busca en el usuario. Tiene que existir %USERPROFILE%\.cursor\skills\security-compliance\SKILL.md (o la misma carpeta bajo .claude\skills, o la variable TEAM_AI_SECURITY_SKILL).

Pedile a quien ya lo tenga en el equipo la carpeta de esa skill y copiala a C:\Users\<tu-usuario>\.cursor\skills\security-compliance\. Si falta, /security-review deja el gate en NOT_AVAILABLE; no se finge un PASS.

5.4 Inicializar OpenSpec en cada repo de producto

Esto crea /opsx-propose y /opsx-apply dentro del proyecto. Hay que correrlo en backend y, cuando trabajes frontend, también ahí.

cd C:\Maxi\Sistemas\Repos\NWebCore.Backend
openspec.cmd init --tools claude,cursor --profile core --no-animation

cd C:\Maxi\Sistemas\Repos\NWeb.Frontend
openspec.cmd init --tools claude,cursor --profile core --no-animation
Reiniciá Cursor Después del init, Cursor tiene que recargar comandos. Cerrá y abrí el IDE (o al menos la ventana del repo) antes de probar /work-propose.

6. Instalar el kit en cada repo

Siempre desde la carpeta del kit, apuntando --target al repo de producto. Org y proyecto de Azure son fijos para este equipo:

  • Organización: DMEDLATSYS
  • Proyecto: NCSLite

cd C:\Maxi\Repos Propios\developer-ai-kit

node dist/cli.js setup --target C:\Maxi\Sistemas\Repos\NWebCore.Backend --role backend --hosts claude,cursor --org DMEDLATSYS --project NCSLite

node dist/cli.js doctor --target C:\Maxi\Sistemas\Repos\NWebCore.Backend

6.2 Frontend

cd C:\Maxi\Repos Propios\developer-ai-kit

node dist/cli.js setup --target C:\Maxi\Sistemas\Repos\NWeb.Frontend --role frontend --hosts claude,cursor --org DMEDLATSYS --project NCSLite

node dist/cli.js doctor --target C:\Maxi\Sistemas\Repos\NWeb.Frontend

El setup copia las 11 skills a .cursor/skills y .claude/skills, las reglas del rol, MCP, hooks y .ai/kit-manifest.json. Si el backend ya tenía un MCP ado, lo conserva y agrega ado-developer al lado.

No edites las skills generadas Los SKILL.md de .cursor/skills y .claude/skills se regeneran con setup/update. El texto canónico vive en el kit, carpeta skills/.

7. Verificar que quedó instalado

En cada repo de producto tendrían que existir, como mínimo:

  • Las 11 skills en .cursor/skills/<nombre>/SKILL.md y lo mismo bajo .claude/skills
  • .cursor/commands/opsx-propose.md (lo crea OpenSpec, no el kit)
  • .ai/kit-manifest.json con rol backend o frontend
  • .cursor/mcp.json con el servidor ado-developer
  • openspec/config.yaml

Skills del kit: work-item, work-propose, work-apply, verify-change, security-review, security-fix, commit-change, pr-ready, knowledge-backend, knowledge-frontend, knowledge-testing.

Gitignore En estos repos .cursor/, .claude/ y .ai/ suelen estar ignorados. Es normal que git status no muestre las skills. Están en disco para Cursor, no para el remoto.

Abrí el repo de la tarea como carpeta de Cursor (backend o frontend, no el kit). En el chat, los slash /work-item, /work-propose, etc. tienen que aparecer como skills del proyecto.

8. Cómo usar el kit (flujo diario)

Trabajá siempre en el chat de Cursor con el repo correcto abierto. Reemplazá 6551 por el id de tu Work Item.

Paso 1 — Contexto y rama

/work-item 6551

Lee la tarea en Azure (MCP de solo lectura). Si el tech lead te pasó un work-context.json, adjuntarlo en el mismo mensaje. Crea la rama local feature/<id>-<slug> desde sandbox (si no está local, usa origin/sandbox). No hace push.

Revisá .ai/work-items/DMEDLATSYS-NCSLite-<id>/work-context.md:

  • READY — podés proponer.
  • DRAFT o BLOCKED — faltan criterios o un contrato. No pases a /work-propose.

Paso 2 — Plan

/work-propose 6551

Llama a /opsx-propose (Cursor) y escribe openspec/changes/wi-<id>-*/ (proposal.md, design.md, tasks.md). Guarda plan-approval.json de esa versión. No hay que responder “autorizo” en un paso extra.

Leé el plan. Si no es lo que querés, pedí cambios y volvé a /work-propose.

Paso 3 — Código

/work-apply 6551

Implementa el plan actual. Correr apply es la aprobación para codear. Si el resultado no cierra, iterá el código y después actualizá el plan con otro /work-propose.

No inventa firmas de stored procedure ni de API. No pisa cambios ajenos del working tree.

Paso 4 — Gates

/verify-change 6551
/security-review 6551 --changes

Verify corre los checks reales del repo (en backend, el build). Un script ausente queda NOT_AVAILABLE, nunca PASS. Security audita el diff y no modifica código. Si hay hallazgos que hay que arreglar: 

/security-fix 6551
/verify-change 6551
/security-review 6551 --changes

Paso 5 — Commit y PR

/commit-change 6551 --preview
/commit-change 6551
/pr-ready 6551

El preview muestra el mensaje. La segunda invocación hace el commit local, solo con archivos de la tarea, con referencia Azure (#6551). No hace push. /pr-ready arma título y body; el PR se crea solo si lo pedís explícitamente.

Resumen para copiar en el chat /work-item ID → /work-propose ID → /work-apply ID → /verify-change ID → /security-review ID --changes → /commit-change ID --preview → /commit-change ID → /pr-ready ID

9. Qué hace cada comando (sin magia)

ComandoQué haceQué no hace
/work-item Contexto Azure + rama feature/id-slug desde sandbox No propone, no codea, no pushea
/work-propose Plan OpenSpec + plan-approval.json No edita código de producto
/work-apply Implementa el plan actual No inventa contratos SP/API
/verify-change Compara plan vs código y corre checks No marca PASS si la herramienta no existe
/security-review Auditoría del diff No modifica código
/security-fix Remedia findings autorizados No se autoaprueba el gate
/commit-change Commit local del diff de la tarea No push, no git add .
/pr-ready Evalúa READY y exporta work-result No crea el PR ni marca el WI como Done

knowledge-backend, knowledge-frontend y knowledge-testing no se invocan a mano: /work-apply las carga si el cambio toca esa capa.

En Claude Code los nativos de OpenSpec son /opsx:propose y /opsx:apply (con dos puntos). En Cursor son /opsx-propose y /opsx-apply (con guion). No uses /ospx-*.

10. Postman — unirse al team (backend)

Los de backend tienen que estar en el team de Postman del producto para probar las APIs con la colección compartida. Frontend no lo necesita para el flujo del kit.

Unirme al team de Postman

  1. Instalá Postman de escritorio desde postman.com/downloads, o usá la web app.
  2. Entrá con tu cuenta (Google o email de trabajo). Si no tenés cuenta, creala en esa misma pantalla.
  3. Abrí el link de invitación de arriba. Tiene que verse el team al que te están invitando.
  4. Aceptá la invitación. Si el link expiró, pedí uno nuevo a quien administra el team.
  5. En la barra lateral, cambiá el workspace al del equipo (no te quedes en My Workspace personal).
  6. Ahí están las colecciones y environments compartidos. Elegí el environment del ambiente que vas a pegarle (dev / QA / local).
  7. Antes de mandar requests, revisá variables: base URL, token o cookie de sesión. No commitees secretos ni los pegues en el chat del kit.
  8. Cuando pruebes un endpoint de tu tarea, usá la request de la colección si existe. Si no existe, creala en el workspace del team, no en uno privado.
Relación con el kit Postman no lo instala el setup. Es la herramienta para ejercitar las APIs del backend mientras desarrollás. El kit no publica requests ni cambia el Work Item desde Postman.

11. Problemas frecuentes

SíntomaQué hacer
npm.ps1 no está firmado Usá npm.cmd y openspec.cmd.
/opsx-propose no está instalado Falta openspec.cmd init --tools claude,cursor en ese repo. Reiniciá Cursor.
/work-item no cambia de rama Working tree sucio, o no existe sandbox / origin/sandbox. Limpiá o hacé pull de sandbox.
No lee Azure az login, y que exista .cursor/mcp.json con ado-developer. En backend, si ese archivo se perdió, volvé a correr setup.
Doctor marca OpenSpec no instalado El CLI no está en PATH de esa terminal, o no corriste init. Después del init, opcional: node dist/cli.js update --target ... para refrescar .ai/openspec-commands.json.
Security NOT_AVAILABLE Falta la skill security-compliance en %USERPROFILE%\.cursor\skills\.
No aparecen las skills en Cursor Abriste el kit en vez del repo de producto, o hace falta recargar la ventana. Las skills viven en .cursor/skills del backend o frontend.
