1. Qué es este kit

El Developer AI Kit es un procedimiento común para Cursor y Claude Code. No cambia la arquitectura del producto: se instala encima de los repos de backend y frontend y deja skills, reglas y un CLI para trabajar cada Work Item de Azure de la misma forma.

El recorrido de una tarea es:

  1. /work-item — el CLI lee Azure con PAT (igual que tl-control), arma contexto y crea la rama desde sandbox.
  2. /work-propose — genera el plan OpenSpec.
  3. /work-apply — implementa ese plan. Correrlo es la aprobación para codear.
  4. /verify-change y /security-review — gates.
  5. /commit-change y /pr-ready — commit local y preparación del PR. No hay push automático.
Dos repos, dos instalaciones El kit se instala en cada repo de producto, no una sola vez en la máquina. Backend usa --role backend y frontend --role frontend.

2. Requisitos de la máquina

/work-item no usa Azure CLI ni el MCP. El CLI del kit lee Azure igual que tl-control: PAT local AZURE_DEVOPS_EXT_PAT (o AZURE_DEVOPS_PAT) y REST GET. El agente no abre el .env ni pega el token.

2.1 Cadena para que Azure ande

  1. Node.js 20.19 o más (LTS 20 o 22), con npm en el PATH.
  2. PAT de Azure DevOps en un .env local, igual que tl-control (sección 2.3). No va a Git ni al chat.
  3. Permiso en Azure DevOps de lectura de Work Items en DMEDLATSYS / NCSLite.
  4. Internet para el GET a dev.azure.com.
MCP y Azure CLI son opcionales Sirven si querés tools extra en el chat. No bloquean /work-item. Detalle en la sección 6.
Orden y PATH Instalá Node antes de abrir Cursor o Claude Code. Si el host ya estaba abierto, cerralo por completo (no solo la ventana) y volvé a entrar: si no, no ve node recién instalado. Si trabajás solo con Claude Code, no hace falta reiniciar Cursor.

2.2 Instalar Node.js

Bajá el LTS desde nodejs.org (20.19+ o 22). En el instalador de Windows marcá Add to PATH. No uses una versión 18 o menor: el kit pide >= 20.19.0.

Cerrá la terminal, abrí una nueva y comprobá las tres cosas. En PowerShell usá npm.cmd / npx.cmd (sección 3):

node -v
npm.cmd -v
npx.cmd -v
where.exe node
where.exe npx

node -v tiene que ser v20.19 o más. where.exe node tiene que mostrar una ruta tipo C:\Program Files\nodejs\node.exe. Si dice que no encuentra el archivo, Node no está en el PATH: reinstalá marcando Add to PATH o agregá C:\Program Files\nodejs\ a las variables de entorno y reiniciá Windows (o al menos Cursor y la terminal).

2.3 PAT de Azure (igual que tl-control)

El CLI busca AZURE_DEVOPS_EXT_PAT o AZURE_DEVOPS_PAT en este orden:

  1. Variable de entorno de la terminal / proceso.
  2. .env en la raíz del repo de producto (backend o frontend).
  3. .env en la carpeta del kit (developer-ai-kit/.env).
  4. tl-control/.env (el mismo archivo que usa el TL).

Plantilla: developer-ai-kit/.env.example. Copiá la clave, nunca el valor a Git ni al chat. En Azure DevOps: User settings → Personal access tokens, con lectura de Work Items. Si el PAT ya está en tl-control, no hace falta duplicarlo.

No lo pegues Ni en mcp.json, ni en el chat, ni en work-context. El agente no tiene que abrir el .env: lo lee el CLI.

Comprobá sin mostrar el token: node dist/cli.js doctor --target <repo> tiene que decir PAT Azure (tl-control) presente. Si dice “Sin PAT”, falta el .env.

2.3b Azure CLI (solo si usás MCP)

No hace falta para /work-item. Si querés el servidor MCP ado-developer, instalá Azure CLI y hacé az login (detalle en la sección 6).

3. PowerShell: usá npm.cmd y openspec.cmd

En Windows, si PowerShell tiene la política de ejecución restringida, npm y openspec fallan con “el archivo npm.ps1 no está firmado digitalmente”. No hace falta cambiar la política. Llamá al .cmd: 

npm.cmd -v
npm.cmd install -g @fission-ai/openspec
openspec.cmd --version

node y git no tienen ese problema. El resto de esta guía usa npm.cmd / openspec.cmd para que copie y pegue sin fricción.

5. Paquetes y herramientas externas

Esto se hace una vez por máquina, salvo OpenSpec init, que se corre en cada repo de producto.

5.1 OpenSpec (CLI global)

El kit no implementa el plan: llama a OpenSpec. Sin este CLI, Cursor no tiene /opsx-propose ni /opsx-apply.

npm.cmd install -g @fission-ai/openspec
openspec.cmd --version

Tiene que mostrar una versión (en el equipo se validó 1.14.1).

5.2 PAT Azure

Igual que tl-control: AZURE_DEVOPS_EXT_PAT en un .env local. Pasos en la sección 2.3. MCP (opcional) en la sección 6.

5.3 Skill de seguridad security-compliance

El kit no copia el auditor: lo busca en el usuario. Tiene que existir %USERPROFILE%\.cursor\skills\security-compliance\SKILL.md (o la misma carpeta bajo .claude\skills, o la variable TEAM_AI_SECURITY_SKILL).

Pedile a quien ya lo tenga en el equipo la carpeta de esa skill y copiala a C:\Users\<tu-usuario>\.cursor\skills\security-compliance\. Si falta, /security-review deja el gate en NOT_AVAILABLE; no se finge un PASS.

5.4 Inicializar OpenSpec en cada repo de producto

Esto crea /opsx-propose y /opsx-apply dentro del proyecto. Hay que correrlo en backend y, cuando trabajes frontend, también ahí.

cd C:\Maxi\Sistemas\Repos\NWebCore.Backend
openspec.cmd init --tools claude,cursor --profile core --no-animation

cd C:\Maxi\Sistemas\Repos\NWeb.Frontend
openspec.cmd init --tools claude,cursor --profile core --no-animation
Reiniciá Cursor Después del init, Cursor tiene que recargar comandos. Cerrá y abrí el IDE (o al menos la ventana del repo) antes de probar /work-propose.

6.2 Instalar el paquete MCP (Node / npm)

No hace falta un npm install dentro del repo de producto. Cursor usa npx -y y baja @azure-devops/mcp@2.10.0 al cache de npm la primera vez (puede tardar 30–60 s y necesita red). Si querés dejarlo listo de antemano:

npx.cmd --yes @azure-devops/mcp@2.10.0 --help

Si ese --help falla con “npx no se reconoce”, Node no está en el PATH: volvé a la sección 2.2.

6.5 Activarlo en Cursor

  1. Guardá los JSON en el repo que tenés abierto.
  2. Reiniciá Cursor (o recargá la ventana).
  3. Andá a Settings → MCP (o Cursor Settings → Tools & MCP).
  4. Tiene que aparecer ado y ado-developer. Si pide Allow / Enable, aceptá.
  5. La primera corrida de npx puede tardar mientras baja el paquete. Hace falta red.
  6. Si el servidor queda en rojo: az login, confirmá node -v y npx.cmd -v en una terminal nueva, y reiniciá Cursor por completo.
  7. Si Cursor dice que no encuentra npx, Node se instaló con Cursor abierto: cerralo del todo y abrilo de nuevo.

6.6 Activarlo en Claude Code

Claude Code lee .mcp.json en la raíz del repo (no .cursor/mcp.json). Si trabajás solo con Claude, los pasos de “reiniciar Cursor” no aplican.

  1. Guardá .mcp.json (sección 6.4) en el repo de producto.
  2. Cerrá Claude Code y abrilo de nuevo en ese repo (backend o frontend, no el kit).
  3. Confirmá que el servidor ado-developer aparece conectado. La primera corrida de npx puede tardar.
  4. Si queda en rojo: az login, node -v, npx.cmd --yes @azure-devops/mcp@2.10.0 --help, y reabrí Claude Code.
Qué usa el kit /work-item lo ejecuta el CLI con PAT local (REST GET). Si el MCP está conectado, el hook bloquea tools *_write. No cambies estado, asignación ni sprint desde el chat.
Estos archivos suelen estar en .gitignore Cada developer los pone en su disco. El setup del kit también escribe ado-developer; si el backend ya tenía ado, lo deja y suma el del kit. Si .cursor/mcp.json desaparece, volvé a pegar el JSON de arriba o corré setup de nuevo.

7.3 Cómo encuentra el CLI el agente

/work-item no corre “mágicamente”: el agente tiene que ejecutar el CLI compilado del kit desde el repo de producto. El setup deja esa ruta absoluta (en esta máquina, la carpeta donde clonaste el kit) en tres lugares:

  • CLAUDE.md y AGENTS.md — bloque del kit: node "<corePath>/dist/cli.js"
  • Skills generadas (.claude/skills y .cursor/skills) — ya no queda el placeholder <kit>
  • .ai/kit-manifest.json → source.corePath

Comprobá después del setup (ajustá la ruta si tu clon no está en el ejemplo): 

node dist/cli.js doctor --target C:\Maxi\Sistemas\Repos\NWebCore.Backend

Tiene que figurar OK [installed] CLI del kit resoluble y PAT Azure (tl-control) presente (sin mostrar el token). El chequeo “MCP autenticado” queda en rojo a propósito: MCP no es requisito de /work-item.

No uses npx team-ai Ese comando busca un paquete npm que no está en el repo. Backend ni siquiera tiene package.json. Tampoco instales el kit con npm link salvo que sepas lo que implica. Si movés la carpeta del kit, volvé a correr update para reescribir la ruta.

8. Actualizar el Developer AI Kit

Si el kit ya estaba instalado y /work-item fallaba (MCP 1.4.0 o npx team-ai), el procedimiento corto está arriba: Si ya lo tenías instalado. Esta sección es el mismo flujo, con más detalle, para cualquier actualización futura del kit.

El kit vive en un repo aparte (developer-ai-kit). Los repos de backend y frontend no traen el kit por Git: cada máquina tiene una copia del repo del kit y el CLI escribe skills, reglas y archivos bajo .cursor/, .claude/ y .ai/ en el repo de producto. Cuando el equipo sube cambios al kit (nuevas skills, reglas o versión), hay que actualizar el repo del kit en tu PC y después correr update en cada repo donde ya hiciste setup.

8.1 Actualizar el repo developer-ai-kit en tu máquina

  1. Abrí una terminal en la carpeta donde clonaste el kit (por ejemplo C:\Maxi\Repos Propios\developer-ai-kit).
  2. Traé los cambios del remoto: 
    cd C:\Maxi\Repos Propios\developer-ai-kit
git pull
  3. Recompilá el CLI (obligatorio si cambió código TypeScript): 
    npm.cmd install
npm.cmd run build
  4. Opcional: mirá la versión del core: 
    node dist/cli.js version
Sin git pull no alcanza Correr update con una carpeta del kit vieja solo regenera archivos con la versión que tengas en disco. Siempre pull + npm run build antes de actualizar los repos de producto.

8.2 Aplicar la actualización en backend y frontend

El comando update vuelve a ejecutar el setup de forma segura: regenera skills y archivos administrados, hace backup de lo que cambia en .ai/backups/, conserva el manifiesto y no pisa tu código de negocio. Si no existía kit instalado, hace un setup completo.

Primero podés simular sin escribir:

cd C:\Maxi\Repos Propios\developer-ai-kit

node dist/cli.js update --target C:\Maxi\Sistemas\Repos\NWebCore.Backend --role backend --hosts claude,cursor --org DMEDLATSYS --project NCSLite --dry-run

node dist/cli.js update --target C:\Maxi\Sistemas\Repos\NWeb.Frontend --role frontend --hosts claude,cursor --org DMEDLATSYS --project NCSLite --dry-run

Si el dry-run se ve bien, aplicá sin --dry-run en cada repo que uses:

node dist/cli.js update --target C:\Maxi\Sistemas\Repos\NWebCore.Backend --role backend --hosts claude,cursor --org DMEDLATSYS --project NCSLite

node dist/cli.js update --target C:\Maxi\Sistemas\Repos\NWeb.Frontend --role frontend --hosts claude,cursor --org DMEDLATSYS --project NCSLite

node dist/cli.js doctor --target C:\Maxi\Sistemas\Repos\NWebCore.Backend
node dist/cli.js doctor --target C:\Maxi\Sistemas\Repos\NWeb.Frontend

Si ya tenías .ai/kit-manifest.json, update reutiliza rol y hosts del manifiesto si no pasás --role / --hosts; igual conviene pasarlos explícitos para no equivocarse.

8.3 Después del update

  1. Recargá el host que uses: Cursor (cerrá y reabrí) y/o Claude Code en el repo de producto. Si solo usás Claude, no hace falta tocar Cursor.
  2. Revisá que doctor no marque drift grave en archivos generated. Si editaste a mano un SKILL.md generado, el update lo va a sobrescribir: los cambios van al repo developer-ai-kit, carpeta skills/.
  3. Tu .cursor/mcp.json con el servidor ado del equipo se conserva; el kit vuelve a mergear ado-developer. Si borraste ado, volvé a pegar el JSON de la sección 6.
  4. OpenSpec (openspec init) no se repite sola: si el kit pide comandos nuevos de OpenSpec, seguí el aviso del doctor.
  5. Los datos de tareas en .ai/work-items/ y reportes locales no se pierden con un update normal.
Qué no hace el update No actualiza Node, Azure CLI, OpenSpec global ni la extensión Jam. No hace git pull de NWebCore.Backend ni NWeb.Frontend. No commitea ni pushea nada.

8.4 Si algo sale mal

  • Backups: .ai/backups/<timestamp>/ en el repo de producto, copia de archivos que el kit reemplazó.
  • doctor compara versión instalada vs la del CLI que acabás de compilar.
  • Para quitar solo lo del kit: node dist/cli.js uninstall --target ... --dry-run y luego sin dry-run. No toca tu código fuente del producto.

Trabajá siempre en el chat de Cursor o Claude Code con el repo correcto abierto. Reemplazá 6551 por el id de tu Work Item. El agente tiene que poder ejecutar el CLI de la sección 7.3; si npx team-ai falla, está leyendo instrucciones viejas: corré update.

Paso 1 — Contexto y rama

/work-item 6551

12. Postman — unirse al team (backend)

Los de backend tienen que estar en el team de Postman del producto para probar las APIs con la colección compartida. Frontend no lo necesita para el flujo del kit.

Antes de probar en Postman Tenés que tener NWebCore.Backend levantado en tu máquina (o apuntar Postman al host/puerto donde corre). Si el API no responde, revisá la sección 13 (config y base de datos).

Unirme al team de Postman Video: cómo usar Postman

El video en Jam muestra token, variable {{token}}, workspace compartido y una prueba contra el entorno. La API tiene que estar corriendo: normalmente el backend local que configuraste en la sección 13.

  1. Instalá Postman de escritorio desde postman.com/downloads, o usá la web app.
  2. Entrá con tu cuenta (Google o email de trabajo). Si no tenés cuenta, creala en esa misma pantalla.
  3. Abrí el link de invitación de arriba. Tiene que verse el team al que te están invitando.
  4. Aceptá la invitación. Si el link expiró, pedí uno nuevo a quien administra el team.
  5. En la barra lateral, cambiá el workspace al del equipo (no te quedes en My Workspace personal).
  6. Ahí están las colecciones y environments compartidos. Elegí el environment del ambiente que vas a pegarle (dev / QA / local).
  7. Token de las APIs: entrá a NWEB DEV, iniciá sesión y copiá el token de autenticación de una request que ya lo mande (header Authorization o el campo que use el material de referencia). Pegalo en la variable de Postman {{token}} del environment del team. No lo commitees ni lo pegues en el chat del kit.
  8. Antes de mandar requests, revisá también base URL y el resto de variables del environment (dev / QA / local).
  9. Cuando pruebes un endpoint de tu tarea, usá la request de la colección si existe. Si no existe, creala en el workspace del team, no en uno privado.
Relación con el kit Postman no lo instala el setup. Es la herramienta para ejercitar las APIs del backend mientras desarrollás. El kit no publica requests ni cambia el Work Item desde Postman.

13. Backend local — config para probar con base de datos

Para validar una tarea de backend con Postman (o con NWEB DEV) no alcanza con el kit: tenés que poder correr NWebCore.Backend en local y que hable con la base de datos y servicios que use tu cambio. Eso se hace ajustando los archivos de configuración del repo. No commitees esos cambios si son solo para tu máquina.

13.1 Levantar el API

  1. Abrí el repo NWebCore.Backend en Visual Studio, Rider o la terminal.
  2. Revisá que compila: dotnet build NWebCore.Backend.csproj.
  3. Ejecutá el proyecto (F5 o dotnet run --project NWebCore.Backend.csproj).
  4. Anotá la URL y el puerto que usa (suelen estar en Properties/launchSettings.json, perfil https o http).
  5. En Postman, la baseUrl del environment tiene que coincidir con ese host/puerto si probás contra tu instancia local.

13.2 Archivos de config que suele tocar el equipo

Los nombres exactos pueden variar; pedí al TL o copiá un ejemplo de quien ya tenga el entorno andando. Lo habitual en .NET:

ArchivoPara qué
appsettings.json / appsettings.Development.json Cadenas de conexión a SQL, URLs de servicios internos, flags de ambiente. Acá va la BD a la que querés pegarle en dev.
Properties/launchSettings.json Puerto, URL de arranque, variables de entorno al depurar. Útil si Postman no llega al API.
Otros *.json de config del repo Integraciones (mensajería, auth, etc.). Solo cambiá lo que tu tarea necesite; no copies prod a ciegas.

13.3 Buenas prácticas

  1. Usá base de datos y servicios de desarrollo, nunca producción, salvo política explícita del equipo.
  2. Si el repo tiene appsettings.Development.json local o secrets de usuario, preferí eso en lugar de editar el JSON que va al remoto.
  3. Antes de commitear, revisá git status: no subas connection strings, passwords ni tokens en appsettings.json.
  4. Probá el flujo de tu tarea (Postman o UI) solo cuando el backend arranque sin errores de conexión a BD.
  5. La evidencia de cierre sigue siendo Postman en el workspace compartido (metodología de tareas); el backend local es el paso previo.
Sin acceso a BD Si no tenés connection string o VPN, no inventes credenciales. Pedí el paquete de config al equipo o marcá la tarea como bloqueada hasta tener ambiente.

14. Jam — grabar videos y reportar bugs

Jam es la extensión de Chrome para grabar la pantalla, sacar capturas y armar un reporte con contexto (pasos, consola, red). La usan backend y frontend cuando hay que mostrar un bug, un flujo o el resultado de una tarea.

Instalar Jam en Chrome

14.1 Instalar la extensión

  1. Abrí Chrome (o un Chromium compatible con Chrome Web Store: Edge también suele servir).
  2. Entrá al link de arriba: Jam en Chrome Web Store.
  3. Clic en Add to Chrome / Agregar a Chrome y confirmá Add extension.
  4. Fijá el ícono: puzzle de extensiones (arriba a la derecha) → Jam → pin / chincheta, para tenerlo a mano.
  5. La primera vez pedí crear cuenta o iniciar sesión en Jam. Usá el mail de trabajo si el equipo comparte grabaciones.
  6. Chrome va a pedir permiso de grabar pantalla y, a veces, de micrófono. Aceptá; si lo bloqueás, la grabación no arranca.

14.2 Cómo grabar

  1. Abrí la pantalla donde se reproduce el problema (app local, QA, Azure, etc.).
  2. Clic en el ícono de Jam.
  3. Elegí Record (video) o screenshot. Para un bug, preferí video corto del flujo.
  4. Seleccioná pestaña, ventana o pantalla completa. Grabá el repro de punta a punta, sin datos de producción ni passwords en cámara.
  5. Pará la grabación. Jam arma un resumen, pasos y suele adjuntar consola / red. Podés anotar o poner voz si hace falta.
  6. Copiá el link de esa Jam y pegalo en el comentario del Work Item, en el chat de la tarea o junto al PR. No subas el MP4 pesado al repo.
Relación con el kit Jam no lo instala el setup. Es para evidenciar el bug o el resultado. En /work-item un adjunto o un link de Jam cuenta como evidencia, no como orden de shell. No grabes secretos, tokens ni datos personales.
Chrome, no Cursor La extensión vive en el navegador. Si trabajás la app en otro browser, grabá esa pestaña o toda la pantalla. Si el ícono no aparece, revisá chrome://extensions y que Jam esté habilitada.
